# Agent factories trade roles for verification

The baseline has shifted since early 2026: the best-documented factories no longer run a standing team of role agents that poll a tracker. They run one isolated worker per task, dispatched by ordinary code, fenced by deterministic steps and capped retries, and judged by something the worker cannot influence, with a human still merging almost everywhere. Gumloop's Factory (October 2026) is the cleanest startup statement of this shape: a manager agent that never codes, rented coding agents treated as swappable tools, "proof" required on every PR, and **571 merged agent PRs in six weeks with 83% needing no human code changes**, all self-reported and limited to work "with an obvious, verifiable solution" ([Gumloop](https://www.gumloop.com/engineering/software-factory)). The DeepSeek Harness "Super-agent" article argues the same split from first principles, a Router with no Bash tool and hidden Worker sessions, backed only by a small synthetic scheduling experiment ([X article](https://x.com/DeepSeekHarness/status/2116857257245987236)). Stripe, Ramp, Spotify, Cursor, StrongDM and Anthropic independently report that their first designs failed and that the fix was removing capabilities from a role instead of prompting it to behave. Nightshift's durable choices still hold (tracker as system of record, human merge, YAML presets, per-role models, a separate reviewer), but its LLM-driven polling, label mutex, fixed role worktrees, LLM tester and single-harness coupling have been superseded. The evidence underneath all of this is weak: almost every throughput number is self-reported, nobody publishes post-merge defect rates, and no non-code factory has published measured results. A cleaner nightshift is a small deterministic dispatcher with pluggable tracker, workspace, harness, verifier and approval ports, where "dev" and "content" are packs that differ mainly in what counts as proof and where the human gate sits.

## The baseline moved from role teams to one worker per task on code-driven rails

### Gumloop: lines, a manager that does not code, and proof before a PR

Gumloop's Factory is organised into "lines", each one kind of maintenance work (agent latency, slow endpoints, CI health, platform improvements) with a human owner. A trigger (a daily telemetry read or a ping) opens a Linear issue; the issue starts a worker, which is a Gumloop agent that reads the engineering skills, conventions and the line owner's preferences and "hands the job to a coding agent"; the coding agent returns a PR with proof, concretely "a test that fails before the fix and passes after it"; an engineer reviews and merges, because "The Factory never merges its own work" ([Gumloop](https://www.gumloop.com/engineering/software-factory)). Jobs that are duplicates, already fixed or not reproducible close without a PR, and a fingerprint memory stops the same problem being picked up twice.

Three details matter for design. First, the coding agent is "a tool the worker calls", chosen per line. The Factory started on Cursor cloud agents; a Cursor outage on September 17 stopped work, and on September 29 one line moved to Devin, after which "Nothing else in the Factory changed". That sentence refers to the harness swap, not to the outage, a point the excerpt-based notes had wrong. Cursor wrote 521 of the 571 merged PRs and Devin 50; Codex, Factory's Droid and Claude Code are named as candidates. Second, mid-task human input is a structured escalation: the worker posts a question, its own recommended pick and the evidence to the line owner in Slack, then "remembers the answer for every job after". Third, outcomes are classified: Merged (Clean), Merged (Automated Fixes), Merged (Human Edits), Merged (Human Authored). Of 556 closed agent-written PRs, 335 merged clean, 128 after automated fixes to AI-review-bot comments, and 93 needed human edits ([Gumloop](https://www.gumloop.com/engineering/software-factory)).

The team credits written-down skills for most of the gain: "In five weeks, we wrote or edited 94 skills, and PRs that merged with no human edits rose from 57% to 89%." It also reports that cutting bloated AGENTS.md files by 44% was followed by a 20% lower median run cost. These are the authors' attributions, not controlled results; the same weeks saw a second harness added. The post names no models, describes no sandbox design, gives no revert or incident rate, and asserts without example that "The same shape works for marketing, for ops". Gumloop sells the orchestration layer the post describes.

### DeepSeek Harness: remove the orchestrator's ability to execute

The X post is only a link to an X Article, "Exploring Super-agent Design: Towards a More Autonomous Agent System", published 1 November 2026 and explicitly labelled as architectural ideas, "not an introduction to existing features of DeepSeek Harness" ([X article](https://x.com/DeepSeekHarness/status/2116857257245987236)). Its complaint is that agents use the session as the unit of work, so "multi-tasking is limited by human attention", which the authors put at 3 to 5 active sessions per person. Its answer has five modules. A long-lived **Router** takes all human interaction and dispatches tasks; it "can run without a Bash tool at all" and suits a lighter model. **Workers** each get an isolated context and full tools for one task, never talk to humans, and need the most capable models. **Triggers** are environmental events filtered in two stages, code first (source and allowlist rules), then an LLM on the survivors; follow-up events in the same thread pass straight to the subscribed Worker without the Router. Long tool calls become asynchronous `start()`/`stop()` calls. Compute, session state and execution environment are separated, with a stateless daemon on the user's own machine ("BYOM") as one execution target, citing Anthropic's Managed Agents as the same idea. Finally an external **Watchdog** session judges whether each Worker "is making substantive progress or drifting", because "Many anomalies are not crashes".

The experiment is small and synthetic: about 300 messages per run with about 20 work requests, five runs per design, and coding simulated by a tool that only consumes time. A single session with a subagent tool and a neutral prompt delegated in **0 of 5 runs** (p95 completion 29.5 minutes); with a delegation-first prompt it delegated in 4 of 5; the two-level design held p95 at 15.7 minutes while using 23.2M cache-read tokens against 6.1M to 10.8M. The article calls this "indicative only", and it measures scheduling, not output quality. It also concedes that security is unsolved: a compromised agent loop could take over every connected device, so "The agent therefore needs a way to use credentials without ever seeing them." The transferable lesson is narrow and solid: do not rely on a prompt to make a coordinator delegate.

### Big companies: one task, one sandbox, one PR, bounded retries

Stripe's Minions run "a Slack message" to "a pull request which passes CI and is ready for human review, with no interaction in between", at over 1,000 and later **over 1,300 merged PRs a week** ([Stripe Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents); [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). Each run gets a pre-warmed devbox, ready in 10 seconds, with no production access or internet egress, which gives "parallelization without the overhead of something like git worktrees, which wouldn't scale at Stripe". Runs follow blueprints, "workflows defined in code" whose nodes are either deterministic (run linters, push) or an agent loop (implement, fix CI). CI is capped at two rounds, then the branch returns to a human. Stripe names no model and no merge or revert rate.

Ramp's Inspect runs each session in a Modal sandbox built from an image refreshed every 30 minutes, uses OpenCode because it is "structured as a server first", supports "all frontier models", and opens PRs under the requesting user's GitHub token so nobody can approve their own agent's change. Ramp's own post reports about 30% of merged PRs and recommends one metric above the rest: "how many sessions result in a merged pull request" ([Ramp](https://builders.ramp.com/post/why-we-built-our-background-agent)). Later figures of "over half" and "three of every four" come from vendor case studies, not Ramp's post ([Modal](https://modal.com/blog/how-ramp-built-a-full-context-background-coding-agent-on-modal); [Linear](https://linear.app/customers/ramp)).

Spotify's Honk wraps the agent in a small internal CLI precisely so it can "seamlessly switch between different agents and LLMs", after Goose, Aider and a homegrown loop all failed to produce mergeable PRs reliably; Claude Code is its current best performer ([Spotify Part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1); [Spotify Part 2](https://engineering.atspotify.com/2025/11/context-engineering-background-coding-agents-part-2)). Its verifiers are hidden from the agent ("the agent doesn't know what the verification does and how") and run from a stop hook before any PR opens; an LLM judge vetoes "about a quarter" of sessions and the agent course-corrects "half the time" ([Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). A report that Spotify later removed the judge rests on a secondary source the researchers did not read ([InfoQ](https://www.infoq.com/presentations/spotify-ai-codebase-migration-agent/)).

Cursor's research harness is the multi-agent exception, and its history is a catalogue of failed coordination designs. Equal agents sharing a lock file made twenty agents perform like "two or three"; a rigid planner/executor/judge cycle was "bottlenecked by the slowest worker"; a continuous executor given "too many roles and objectives simultaneously" slept, did work itself and claimed completion early; an integrator role "created more bottlenecks than it solved". The final design is a root planner that "does no coding itself", recursive sub-planners, and isolated workers on their own repo copies that return one written handoff ([Cursor scaling](https://cursor.com/blog/scaling-agents); [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)). Cursor's own staff describe week-long runs as something that "only *kind of* works right now" ([Lee Robinson](https://x.com/leerob/status/2019460151074259219)).

StrongDM sits at the far end: "Code must not be written by humans", "Code must not be reviewed by humans", validation by holdout scenarios stored outside the codebase and run against behavioural clones of Okta, Jira, Slack and Google services ([StrongDM](https://factory.strongdm.ai/)). Its spending rule is "If you haven't spent at least $1,000 on tokens today per human engineer, your software factory has room for improvement"; one of the research notes had this reversed. It is a three-person team and publishes no escape rate.

Anthropic's own posts trace the arc in under a year. The February 2026 C-compiler project ran sixteen agents in a bash `while true` loop that claimed work by committing lock files to a shared git repo, at just under $20,000, and concluded that "the task verifier is nearly perfect, otherwise Claude will solve the wrong problem" ([Anthropic compiler](https://www.anthropic.com/engineering/building-c-compiler)). The March harness post split planner, generator and evaluator because "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work", then removed sprints once Opus 4.6 made them unnecessary: "every component in a harness encodes an assumption about what the model can't do on its own" ([Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Managed Agents then separated session log, stateless harness and sandbox, with tokens "never reachable from the sandbox" ([Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents)).

### Open-source orchestrators converge on five parts and four standards

The open-source field has the same skeleton regardless of branding: a work ledger, a dispatcher, a per-task workspace, a harness adapter and a merge gate. OpenAI's Symphony is the smallest clear reference: a spec plus an Elixir implementation in which a single orchestrator process polls Linear every 30 seconds, creates one workspace directory per issue, caps concurrency at 10 agents and 20 turns by default, retries with exponential backoff, detects stalls after five minutes, and keeps tracker secrets out of the agent process. It holds no database and is written around the Codex app-server only ([Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)). Gas City generalises further, with session backends for tmux, subprocess, ACP and Kubernetes and "packs" that bundle agents, formulas and schedules ([Gas City](https://github.com/gastownhall/gascity)). Paperclip adds atomic checkout, a database-backed wakeup queue, budgets with hard stops and approval settings of Allowed, Ask first or Off on external actions ([Paperclip](https://github.com/paperclipai/paperclip)).

Four standards carry weight. AGENTS.md and Agent Skills (`SKILL.md` folders with progressive disclosure) are the portable instruction formats ([AGENTS.md](https://github.com/agentsmd/agents.md); [Agent Skills](https://github.com/agentskills/agentskills)). MCP is the tool plane. The Agent Client Protocol is the nearest thing to a common "drive a session" interface: its registry lists 46 agents, including adapters for Claude, Codex, Gemini, Cursor, Copilot, OpenCode, Goose and Devin, at stable version 1 with a v2 in draft ([ACP registry](https://github.com/agentclientprotocol/registry)). A2A shows no use between coding harnesses in any orchestrator README the researchers read. Dependence on GUI orchestrators is risky: Vibe Kanban is sunsetting, Crystal is deprecated, and Meta acquired Conductor this month ([Vibe Kanban](https://github.com/BloopAI/vibe-kanban); [Crystal](https://github.com/stravu/crystal); [Axios](https://axios.com/2026/11/04/meta-acquires-ai-coding-startup-conductor)). Worktrees remain the local default but, as one project's README puts it, they "do not sandbox processes or prevent merge conflicts" ([Paradev](https://github.com/superset-sh/superset)).

## Verification sets the autonomy ceiling, and the evidence is thinner than the headlines

Every account that explains its limits explains them through verification. Spotify ranks its failure modes and calls "a PR that passes CI but is functionally incorrect" the most serious because it "erodes trust in our automation"; in its dataset migrations, repositories without build-time tests forced owners back to manual testing ([Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3); [Spotify Part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)). StrongDM moved validation outside the repo after agents wrote `return true` to pass narrow tests. Anthropic watched its evaluator "identify legitimate issues, then talk itself into deciding they weren't a big deal". The common principle is that the judge must differ from the generator in context, information or kind: a clean-context reviewer, hidden scenarios, or deterministic CI.

Three conclusions follow. First, the measured evidence supports stage separation and independent judgement, and contradicts peer agents editing shared code. Cognition's April 2026 position, one writer with extra agents contributing analysis and a reviewer that shares no context with the coder, is vendor testimony but matches CooperBench ([Cognition](https://cognition.com/blog/multi-agents-working)). Second, AI code review is a recall-adding filter, not a gate: the best published tools score F1 around 0.3 to 0.5 and the benchmarks are vendor-run ([Augment Code](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)). Third, no source in the notes reports post-merge defect, revert or incident rates for agent-written changes from a named factory, and none reports cost per merged change. METR now labels its "19% slower" result historical and has no clean replacement ([METR](https://metr.org/blog/2026-02-24-uplift-update/)). The Faros and GitClear telemetry describes AI-assisted teams broadly, not disciplined factories, so it shows what happens when generation scales without verification, which is the scenario a factory exists to avoid.

Security evidence is incident-based and secondary, but consistent. A prompt injection in a GitHub issue title hijacked Cline's triage agent and led to a malicious package release; an agent with an over-privileged token wiped a production database and its backups ([Clinejection](https://ai-era.pages.dev/incidents/clinejection); [Mondoo](https://mondoo.com/blog/5-lessons-from-9-seconds-ai-agent-deleted-production-database)). Any stage that reads issue text processes attacker-controlled input, and the durable mitigations are architectural: sandbox the run, scope credentials, and keep them out of the process that executes generated code.

## Non-code factories are linear skill chains gated at the publish action

No named company has published a fully autonomous marketing or content factory with measured outcomes. What exists is narrower and more instructive. Anthropic's growth-marketing workflow is a slash command that checks ad copy against Agent Skills for brand voice, product accuracy and platform rules, then emits an upload-ready CSV of 15 headlines and 4 descriptions; a human reviews every line and uploads by hand ([Claude blog](https://claude.com/blog/how-anthropic-uses-claude-marketing)). Semrush rebuilt a content-update pipeline from n8n into Claude Code as nine skills run in fixed order by a master script, from SERP research through a semantic-similarity check and product-mention audit to a draft, because the drafting step "never worked" in the workflow builder; its results are qualitative and the notes rest on search excerpts ([Semrush](https://www.semrush.com/blog/how-i-rebuilt-our-content-update-pipeline/)). Clay is porting versioning, test environments and logs to sales plays under a "GTM CI/CD" label, by its own account still in progress ([Clay](https://www.clay.com/blog/gtm-self-learning-loops)). The time savings Anthropic reports (30 minutes per ad to 30 seconds) are first-party with no method.

Three structural differences from code decide the design. There is no test suite, so "done" becomes a ladder: hard format constraints, every factual claim mapped to a supplied source, a rubric judge with binary criteria calibrated against human labels, a named human approver, and metrics recorded after publication. Only the first two behave like tests; guidance that an LLM judge should reach a Cohen's kappa of 0.61 against human labels is a convention, not a validated standard ([Chrome for Developers](https://developer.chrome.com/docs/ai/evals/expert-judge)). Second, the irreversible step is publishing, not merging: a sent email or indexed page cannot be reverted, so the approval belongs on the external action. Third, volume is itself a risk. In a self-reported agency survey, 36.5% of marketers said hallucinated or incorrect AI content had already been published, and Google's scaled-content-abuse enforcement targets exactly what a throughput-optimised content factory produces ([PPC Land](https://ppc.land/nearly-half-of-marketers-encounter-ai-errors-weekly-as-study-exposes-trust-gap/); [Search Engine Journal](https://www.searchenginejournal.com/scaled-ai-content-often-fails-googles-crawl-economics-explain-why/)). One agency says its pipeline stopped shipping slop only after the editor got a veto the director could not override, an organisational restatement of the independent-evaluator rule ([Architech](https://www.architech.ca/insights/we-built-an-ai-content-pipeline-and-it-shipped-slop)).

What transfers from code is everything that does not depend on tests: files as the artifact store, skills as procedures, a scripted stage order, review as a separate role, lines with owners, escalation with a recommended pick, and remembered preferences. The scarce asset is ground truth. Agent-generated voice documents start generic, and Anthropic's skills depend on example copy written by human copywriters.

The pattern in the table is consistent. Nightshift's early-2026 design resembles Anthropic's February compiler harness (loops plus lock files) crossed with a role org chart. What the year added is a layer of ordinary code between the tracker and the agents, and a shift in where LLM calls are spent: fewer on coordination and status-checking, more on a single well-briefed worker and an independent check of its output.

## A cleaner design is a small deterministic kernel with five ports and domain packs

The design below is this report's synthesis; no vendor-neutral reference architecture has been published.

The **kernel** is a daemon of ordinary TypeScript that owns all control flow. It reconciles on each tick: read candidate work from the tracker, claim atomically in a local ledger, create a workspace, run the pipeline for that item, record the result, project state back to the tracker. It enforces concurrency caps, per-stage round caps, wall-clock and spend limits, backoff and stall detection. No model call is needed to decide that nothing changed. A local append-only run log (SQLite fits a local-first CLI) holds claims, attempts, token usage and outcome class, while the tracker stays the human-facing truth. This hybrid is where Beads' GitHub sync and Emdash's tracker integrations already point.

Five **ports** keep the kernel ignorant of vendors. The tracker port (list, claim, transition, comment, attach) gets GitHub Issues first and Linear second. The workspace port creates one workspace per task, with a worktree implementation for trusted local use and a container or remote-sandbox implementation for unattended runs; for content the same port yields a working folder. The harness port is the narrow interface the orchestrator notes arrive at: start, send, stream events, interrupt, resume, report usage. Claude Code's headless `stream-json` mode is the first adapter, ACP the general one, and a tmux pane the human-attachable fallback; model choice is a per-stage parameter passed through. The verifier port runs checks the worker does not author and cannot edit: commands selected by repository contents, a clean-context reviewer that sees only the diff or draft, and a rubric judge for prose. The approval port carries escalations as question, recommended pick and evidence, to a tracker comment or chat, and writes answers to a per-line preference file that later runs read.

A **pipeline** is data: a short graph whose nodes are either deterministic steps or agent steps, in Stripe's blueprint sense. The dev pipeline becomes triage (code rules, then a cheap model with no shell), an optional plan with a human approval gate for larger work, a single implement step that must produce proof, deterministic lint and test nodes, a capped fix loop, a clean-context review, and a PR. Nightshift's five roles compress to one worker and one reviewer, with producer and tester mostly turned into code.

A **domain pack** bundles a pipeline, its skills, its verifiers and its publish action. This is where dev and content differ, and the differences are few.

| | Dev pack | Content or marketing pack |
|---|---|---|
| Unit of work | Issue to PR | Brief to platform-shaped artifact (draft, CSV, variant set) |
| Proof | Fail-before/pass-after test, CI | Format constraints pass; each claim maps to a fact sheet |
| Independent check | Clean-context reviewer on the diff | Rubric judge calibrated on approved examples; editor veto |
| Irreversible step and human gate | Merge | Publish or upload to an external platform |
| Ground-truth files | AGENTS.md, skills, tests | Voice guide, product fact sheet, approved-examples folder, results log |
| Extra controls | Round caps, sandbox | Throughput caps, entry at any stage |

Three rules keep the design honest over time. Remove capability instead of adding instruction: the triage step has no shell, the worker cannot edit its verifier, the reviewer cannot see the worker's context. Treat every component as an assumption about model weakness and record why it exists, so it can be deleted when a model generation makes it dead weight. And prefer open formats (AGENTS.md, `SKILL.md`, MCP, ACP, pinned by version) over any one orchestrator product, given how many of those changed status in 2026.

## Open design questions worth brainstorming

**Where does the dispatcher live?** A local daemon matches nightshift's local-first character but stops when the laptop sleeps. A GitHub Actions runner (as one Symphony port does) gives always-on dispatch with sandboxing for free but moves execution off the user's subscription login. DeepSeek's stateless-daemon-on-your-machine idea is a third option with an unsolved security model. Which of these does nightshift's user actually want at 3 a.m.?

**How many roles survive?** The evidence supports one writer plus an independent reviewer and says nothing controlled about whether a separate planner session beats a single worker that plans first. Anthropic kept its planner and dropped sprints; Cursor's product version gates on plan approval. Nightshift could keep its planner as an optional node and let the outcome log decide, which requires logging outcomes first.

**What is proof when the repo has weak tests?** Gumloop restricts itself to verifiable work and Spotify fell back to manual testing where tests were absent. For the small repos nightshift targets, is the answer to refuse such tickets, to make "write the failing test" a mandatory first node, or to adopt StrongDM-style scenarios held outside the worktree? The last is the only defence against a worker rewriting its own tests, and nobody has published its escape rate.

**What is proof for content?** A fact sheet and a rubric are only as good as their human-written inputs. Who maintains them, how is the judge calibrated with a few dozen labelled examples, and should a content line refuse to run until those files exist?

**Where should the human sit, and how is their answer remembered?** Before work (plan or brief approval), during work (judgment calls) and at merge or publish are all in use. Gumloop's remembered preferences are the only documented way of asking a question once. Stored as a file per line, such memory is reviewable and prunable; the ETH result on context files warns that an append-only learnings file will add cost without adding success.

**How far should harness-agnosticism go?** ACP gives breadth across 46 agents but lags native features such as hooks and permission modes, and each native adapter is a parser to maintain. A defensible first step is two adapters, Claude Code and one other, purely to prove the interface is real. Whether subscription terms allow orchestrators to drive vendor CLIs was not researched.

**What is the minimum sandbox for a tool that runs on the user's machine?** Worktrees with the user's credentials are acceptable for a private repo with trusted issue authors and unacceptable for a public one. A container workspace with brokered Git credentials is the obvious next tier; how much setup friction will users tolerate for it?

**Should intake grow beyond tickets?** Gumloop's lines start from telemetry and schedules, and DeepSeek describes speculative "silently reproduce and fix" work that surfaces only on success. Both raise review load, the documented bottleneck: Faros measured review time rising far faster than output. A factory that proposes work needs a queue limit as much as a trigger.

**Who may edit the factory?** Gumloop's Factory flagged its own stale AGENTS.md and humans made the cut; Warp sends self-improvement patches to a human inbox. If nightshift lets agents propose skill edits, the proposer must not be the judge, and a fixed replay set is needed to tell improvement from drift.

**What does nightshift measure?** Sessions that end in a merged PR, Gumloop's four merge classes, human touchpoints per PR and cost per accepted artifact are all cheap to record once a run log exists, and none is recorded by a label state machine alone.

**What is nightshift's niche?** Symphony, Gas City, Paperclip and Multica now occupy the general orchestrator space with far more contributors. A small, preset-driven, local-first tool with real domain packs for content, the area where every large project only asserts that the shape transfers, is a position none of them holds.

## Conclusion

The year's lesson is that orchestration became boring on purpose. The teams with the largest reported output moved decisions out of prompts and into code, shrank the cast of agents, and spent their design effort on the two places a model cannot be trusted with its own work: deciding what to do next, and deciding whether it is done. For nightshift this is good news, because the parts that need replacing are the cheapest to replace, a polling loop and a label mutex, while the parts that were right, a tracker people already watch, a human at the irreversible step, and behaviour defined in files, are the ones the field kept.

The less comfortable implication concerns content. Code factories work where a test defines done, and the published successes select for that. Content has no such test, publishing cannot be reverted, and more output can reduce the value of all of it. A content pack that copies the dev pack's states will reproduce the documented failures; one built around supplied ground truth, an approval on the publish action and a deliberate throughput limit would be doing something no source in this research has yet shown working, which is both the risk and the opening.
