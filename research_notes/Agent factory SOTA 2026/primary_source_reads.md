## 1. What does https://www.gumloop.com/engineering/software-factory describe?

### Takeaway
Gumloop's Factory is a set of "lines" (one kind of maintenance work each, with a human owner) in which a Gumloop agent acts as engineering manager, opens a Linear issue per job, and calls a rented coding agent (Cursor cloud agents or Devin) that must return a PR with proof; an engineer always merges. The post reports 571 merged agent-written PRs in six weeks with 83% needing no human code changes, and credits written-down engineering skills (94 written or edited in five weeks) for most of the improvement. It says nothing about which models are used or how sandboxes are built.

**Motivation and scope**

Every engineer owns their work end to end, and a lot of that work is low to medium leverage: fixing bugs, speeding up slow endpoints, and hardening the platform. This work has an obvious, verifiable solution but doesn't move the business on its own." — [Gumloop](https://www.gumloop.com/engineering/software-factory)

We call it the Factory, and its workers live in Gumloop." — [Gumloop](https://www.gumloop.com/engineering/software-factory)

**Origin story**
- Agents were slow to start because "Every new feature added a small step to how an agent starts". CTO Rahul Behal "collected a handful of chats that people had reported as slow and opened five VMs side by side. In each one, he pasted the chat link, added what the user reported, and asked a coding agent to read the traces and database, find the cause, and propose a fix." — [Gumloop](https://www.gumloop.com/engineering/software-factory)
- For a reasonable fix "he told it to write a test that reproduces the problem, implement the fix, and make the test pass." For a wrong-shaped fix "he pointed it in a different direction until it found one he liked." — [Gumloop](https://www.gumloop.com/engineering/software-factory)
- The insight: "He spent most of his time waiting for agents, and most of the time they were right. So why was he in the middle?" — [Gumloop](https://www.gumloop.com/engineering/software-factory)
- The design: "a Gumloop agent acts as the engineering manager, and coding agents do the work. We wrote a library of engineering skills, we iterated on the process many times, and eventually it just worked. That became the first line of the Factory." — [Gumloop](https://www.gumloop.com/engineering/software-factory)

**Architecture and components**

It reads our engineering skills, our conventions, and the line owner's preferences, then hands the job to a coding agent." (4) "When the worker needs a judgment call, it asks the line owner in Slack and remembers the answer for every job after." (5) "The coding agent opens a pull request with proof, like a test that fails before the fix and passes after it. An engineer reviews it and merges it. The Factory never merges its own work." — [Gumloop](https://www.gumloop.com/engineering/software-factory)
- "Not every job ends in code. If the problem is already fixed, duplicates another job, or doesn't reproduce, the job closes without a pull request." Jobs without proof close." — [Gumloop](https://www.gumloop.com/engineering/software-factory)
- Six things Gumloop (the platform) supplies around the coding agent: "Triggers. Scheduled and on-demand jobs."; "Connectors for everything. The worker searches Linear and keeps a fingerprint of every problem it has seen, so it doesn't pick up the same job twice." — [Gumloop](https://www.gumloop.com/engineering/software-factory)

**The judgment-call mechanism (human gate 1) and preference memory**
- Worked example: the worker posts "Decision needed · @Marcelo / Question: Can the fix add a stored count to the table? It's a schema change. / Pick: Approve the stored count... / Why: about 90% of the query's CPU goes to the count." The owner replies "I try to avoid backfills as much as possible. - Note the format of the escalation: a question, the worker's own recommended pick, and the evidence. Issue keys use the prefix "FTRY-". — [Gumloop](https://www.gumloop.com/engineering/software-factory)

## 2. What does the X post https://x.com/DeepSeekHarness/status/2116857257245987236 say?

### Takeaway
The post is only a link to a long X Article, "Exploring Super-agent Design: Towards a More Autonomous Agent System", published 1 November 2026 by the DeepSeek Harness account. It is an architecture essay (explicitly not a feature announcement) arguing that an always-on, event-driven agent needs a two-level Router/Worker design, event filtering and subscription routing, asynchronous tool calls, separation of compute from state and from execution environments, and an external watchdog; it backs the routing design with a small synthetic experiment.

**Framing**
- Opening notes: "The original article is in Chinese. This is a machine translation." and "This article discusses architectural ideas. It is not an introduction to existing features of DeepSeek Harness." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- The problem: "Agents still use a single session as the basic unit of work, and sessions are isolated from one another... In our experience, a person can usually follow only 3 to 5 active sessions at once. With these designs, a single task is limited by model capability, but multi-tasking is limited by human attention." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Bolting connectors onto a local agent does not fix it: "It still runs in one synchronous session that blocks on long operations, contexts from different tasks get mixed together, and everything stops whenever the local device goes offline." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Definition: "the agent should be one continuous entity that keeps its context across sessions and works on several complex tasks at once, without the tasks interfering with each other. We call this kind of agent and its system architecture a Super-agent." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Internal use: "our internal Super-agent instance, which runs on DeepSeek Harness, can continue the same development task across IM and GitHub. It also monitors feedback in public group chats and, even when no one @-mentions it, finds root causes on its own and opens Pull Requests to fix them". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Four characteristics: **Continuous** ("it always feels like one agent. They never have to wonder whether session X has information Y in its context"), **Productive** ("It can take the next instruction before the previous command or task has finished"), **Proactive** ("It monitors events in its environment, acts on anything worth handling, and stays quiet otherwise"), **Persistent** ("always online... recovers automatically from anomalies"). "No single ReAct loop can provide all four characteristics at once, so they have to come from the system architecture around it." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Module 1: two-level architecture (Router and Workers)**
- The trade-off: one session for everything gives continuity but "caps how fast a single session can work" and interleaves task details; a session per event maximizes throughput but "the lack of a shared global context leaves their results disconnected. Several sessions replying to the user separately also make the interaction confusing." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Router: "a long-lived global routing layer that receives human interaction from every entry point... the Router layer is designed not to execute tasks itself. It only interacts with humans and dispatches tasks, and it can run without a Bash tool at all." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- How it differs from an agent team: "the Router layer only dispatches tasks and tracks how they relate to each other at a high level. It does not break down individual tasks." and "the Router layer's work is often simpler than expected, and a lighter model can usually provide both speed and quality." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Batching: events arriving during one inference turn "queue up and are processed together in the next turn"; because router steps have "a long input and a short output", "the larger the backlog, the lower the amortized inference time per decision." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Workers: "Each Worker has an isolated context and a full set of execution tools, and is dedicated to a single task. Worker Sessions directly determine the result of each task and the quality of its code, so they usually need the most capable models." "Workers never interact with humans directly... each Worker reports its status to the Router layer, which handles all replies to the user." A Worker "can create subagents or be an Agent Team itself, and this is transparent to the Router layer". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- "Sessions should be an implementation detail of the system, not a mental burden on its users." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Module 2: event-driven Triggers**
- "The agent's main input is no longer prompts that a human types into a session one at a time, but semi-structured events from the environment... group chat messages, emails, calendar reminders, code review comments, and CI results, are called Triggers." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Two-stage filtering: "Programmatic policies (Fast Path): Code runs fast admission checks on deterministic conditions such as the event source, the group, and user or bot allowlists. For example, each source can be set to 'respond only to explicit requests', 'treat as candidate events', or 'ignore'." then "Semantic policies (Slow Path): Candidate events that pass the programmatic checks go to the LLM, which decides whether to act based on the context and on policies written as prompts." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Threads and subscription: "consecutive events on the same GitHub Pull Request, IM topic, or email chain form an event stream, which we call a Thread". "When the Router layer creates a Worker Session for the first event in a Thread, that Worker subscribes to the Thread directly." Then "Subscribed (Fast Path): Code passes follow-up events in the Thread straight through to the subscribed Worker... If a new event falls outside the current task, the Worker can unsubscribe or hand the event back to the Router layer". Subscriptions are many-to-many, which lets overlapping Workers see the same events and "resolve conflicts themselves, without point-to-point communication." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Context organization ("Inline & Spill"): "treat the limited context window as a cache." Inline what is likely needed soon; spill the rest and leave a pointer. Steps: start with the object's ID and a summary; inline related IDs and adjacent content ("the first 50 characters of the content, the IM messages around a message and the one it replies to"); cap long content and leave a pointer. "Wasting the context window is wasting the model's intelligence." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- "Chain of Recall": Triggers, Threads and Worker Sessions get unique IDs that "link the objects into a reference graph"; each recalled object inlines summaries and IDs of next-hop objects so the model can "recall context hop by hop". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Speculative execution: "the agent starts work in the background before it knows whether the result will be used... Results that turn out to be useful are delivered, and the rest are discarded." Example policy "silently reproduce and fix": "It delivers a result only after it has confirmed the issue and found a simple fix. Otherwise, it stays quiet the whole time." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Module 3: full-duplex, multi-channel interaction**
- "we replace time-consuming command and tool calls with asynchronous start() and stop() calls, turning the loop into an asynchronous ReAct loop. A call to start() returns 'Started' immediately... When the tool finishes in the background, the system delivers its final result to the session as a new event message." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- "DeepSeek Harness already implements this asynchronous task mechanism, but it is not yet enabled by default." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Channel norms: for IM, "notify people only when a decision or sign-off is needed, ask only direct questions, and give short conclusions. One simple, effective hard rule we have verified is a cap of 100 words per reply." For GitHub, email and documents, "Deliver structured, information-dense output... write out the full problem background, the change description, and the verification results according to the project's conventions." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Module 4: separating compute, state and environments**
- "local agents tie three things to one device: the compute that runs the Agent Loop, the session state that must persist, and the execution environment". Step one: run the loop "in stateless, elastic cloud containers" and keep "sessions and other persistent state in a database". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Step two: rather than rebuild the environment in a cloud sandbox ("real working environments often include uncommitted local changes, private credentials, dependencies on intranet services, and specific hardware or toolchains. Syncing all of that is expensive, and it is easy to miss something"), leave it in place: "Each endpoint needs only a lightweight daemon, which keeps no session state and does nothing but execute commands and return results." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- It cites Anthropic: "Anthropic's 'Decoupling the brain from the hands' takes the same approach: the harness stays stateless, session logs are stored outside it, and execution environments are connected on demand through a unified interface." The difference claimed: "Our design therefore supports BYOM (Bring Your Own Machine), which connects a user's own development machine or personal computer to the cloud agent. It also supports cloud-hosted machines and compute environments created on demand." Intermittent devices: "when a user's personal device reconnects, the cloud agent automatically starts and completes the tasks that need to run on that device." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Module 5: Watchdog**
- "Many anomalies are not crashes: the process is still running, but the model is stuck in an unproductive loop or has drifted from its goal." "Our external Control Loop is an independent Watchdog Session that runs outside the main system and is driven by scheduled messages. The Watchdog handles infrastructure failures such as API errors and failed state recovery. It also uses the model to judge whether each Worker is making substantive progress or drifting from the overall goal." Maintainers "can ask it in natural language why something failed" and have it adjust prompts or trigger rules while the system runs. — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Experiments (labelled "indicative only")**
- Setup: "Four end-to-end designs ran at the same time, driven by a stream of group chat and GitHub CI messages. Each run had about 300 messages, of which about 20 were work requests... Coding work was simulated by a tool that simply consumes time, so the experiment measures the system's scheduling and coordination, not its ability to execute individual tasks. Each design was run 5 times." Chart caption: "message intervals and work durations scaled by 1/4; model call times not scaled". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Results table (task completion p50 / p95 in minutes; cache-read tokens per run): Super-agent 12.4/15.7, 23.2M; Super-agent without Pass-through 12.6/15.5, 31.8M; Single Session with Subagent tool, neutral prompt 20.4/29.5, 6.1M; Single Session with Subagent tool, delegation prompt 13.8/29.0, 10.8M. — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- The single-session failure: "With the neutral prompt, the model did not call a subagent in any of the 5 runs. All work ran in the main session, new messages kept interrupting it, and p95 reached 29.5 minutes. With the delegation-first prompt, the model delegated in 4 of the 5 runs... In the remaining run, the model judged the work 'small' and did it itself". Conclusion: "A single session has to rely on prompt engineering and the model's on-the-spot judgment to decide whether to delegate. The two-level architecture mitigates this problem at the system level instead". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Pass-through: without it, the "Router makes about 30% more decisions per run, and total cache-read tokens rise from 23.2M to 31.8M, about 37% more. So under this workload, pass-through does not make tasks finish faster or better, but it substantially cuts the Router Session's token use". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Router batching: as arrival rate rose "from about 1 to about 40 per minute, the average batch size increases from 1.0 to 2.8. The time per request grows only from 2.5 s to 3.9 s... so the amortized inference time per decision falls from 6.4 s to 1.6 s." Hence "at our current team size, there is no need to shard the Router layer prematurely". — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Open problems the authors list**
- Scaling: when to shard the Router, when Workers should talk directly; "Once the system has run for months or longer, long-term memory becomes the main bottleneck." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Interaction without sessions: "the chat window became the center of interaction partly through path dependence"; mid-task human intervention is still needed for many tasks. — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Context boundaries and agent-to-agent communication between instances with different permission boundaries. — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- Security: "If a server-side intrusion or a prompt injection compromises the Agent Loop, every endpoint device connected to it could be taken over." and "The agent therefore needs a way to use credentials without ever seeing them." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

**Closing and credits**
- "Rather than proposing new theory, this design applies classic engineering ideas from computer systems to building agent systems." The internal instance "helps every day with reproducing and fixing issues, responding to code reviews, and developing DeepSeek Harness itself." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)
- "Parts of the design in this article are implemented in dsh-superagent-prototype. This plugin is only a prototype for validating the technical approach, not an official DeepSeek product." Linked: github.com/deepseek-ai/dsh-superagent-prototype. "Yujia Qiao implemented the system and wrote the article." — [X article](https://x.com/DeepSeekHarness/status/2116857257245987236)

### Inferences
- This is the clearest public statement of the "one persistent agent, many hidden worker sessions" shape. It maps closely onto Gumloop's manager-plus-coding-agents design, but generalizes the intake side (any event stream, with code-first filtering) and adds two pieces Gumloop does not describe: subscription routing so follow-up events bypass the manager, and an external watchdog that judges progress as well as liveness.
- The experiment tests scheduling only (work is a sleep), on about 20 work requests per run and 5 runs. It supports "a router that cannot do work delegates reliably" and "pass-through saves router tokens"; it says nothing about output quality.
- The article is candid that the approach trades tokens for latency (23.2M versus 6.1M to 10.8M cache-read tokens) and that security is unsolved for the BYOM design.
- The design-level lesson relevant to any factory: do not rely on a prompt to make an orchestrator delegate; remove its ability to execute.

### Gaps
- The GitHub prototype repository was not opened (host outside the allowed list), so I cannot say how much of the design is implemented.
- The Chinese original was not located. Replies and quote posts were not read (the API returns counts only).
- No model names are given for Router or Worker, and no production metrics for the internal instance.
- The account is new (joined June 2026) and the product postdates my background knowledge; I verified only what the API returned, not the account's affiliation with DeepSeek beyond its verified status and website link.

- Context: codebase is "hundreds of millions of lines of code across a few large repositories", mostly "Ruby (not Rails) with Sorbet typing"; "this code moves well over $1 trillion per year of payment volume". — [Stripe Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)
- Isolation: "Devboxes are pre-warmed so one can be spun up in 10 seconds, with Stripe code and services pre-loaded. They're isolated from production resources and the internet, so we can run minions on devboxes without human permission checks. This also gives parallelization without the overhead of something like git worktrees, which wouldn't scale at Stripe." — [Stripe Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents). "A Stripe devbox is an AWS EC2 instance"; "our devboxes already run in our QA environment, and consequently, minions don't have access to real user data, Stripe's production services, or arbitrary network egress." "any mistakes an agent might make are confined to the limited blast radius of one devbox, so we can safely run the agent with full permissions and skip confirmation prompts." — [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Harness: "In late 2024... we internally forked Block's goose... and customized it to work within Stripe's LLM infrastructure." Human-supervised use is left to "third-party tools such as Cursor and Claude Code, which are already made available to our engineers." — [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Blueprints: "Blueprints are workflows defined in code that direct a minion run... a given node can run either deterministic code or an agent loop focused on a task." Agent nodes: "Implement task", "Fix CI failures"; deterministic nodes: "Run configured linters", "Push changes". "In aggregate, we find that 'putting LLMs into contained boxes' compounds into system-wide reliability upside." Teams can write their own blueprints, for example for "tricky LLM-assisted migrations". — [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Rules: "almost all agent rules at Stripe are conditionally applied based on subdirectories". "we standardized on a popular rule format... Cursor's" and "sync our Cursor rules into a format that Claude Code can read as well, so that our three most popular coding agents (minions, Cursor, and Claude Code) can all benefit". — [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Tools: Toolshed "hosts more than 400 MCP tools" in Part 1 and "currently contains nearly 500 MCP tools" in Part 2. "Minions... are provided an intentionally small subset of tools by default, although per-user customizability allows engineers to configure additional thematically grouped sets". "we deterministically run relevant MCP tools over likely-looking links before a minion run even starts". — [Stripe Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents); [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Verification: local lint on push "takes less than five seconds"; CI "selectively runs tests from Stripe's battery of tests—there are over three million of them"; "Many of our tests have autofixes for failures, which we automatically apply." Cap: "we only have at most two rounds of CI... 'often one, at most two, CI runs—and only after we've fixed everything we can locally'". "After the second push and CI run, we send the branch back to its human operator for manual scrutiny." — [Stripe Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents); [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)
- Human gates: "If the code looks good, the engineer opens the PR and requests a review from another Stripe engineer. If not, they can give the minion further instructions". So two humans: the requester, then a reviewer. — [Stripe Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)
- What did not work or was avoided: unconditional global rules ("the agent's whole context window would fill with rules before the agent even starts"); local agents on laptops ("Containerization or git worktrees can help, but they're hard to combine"); unlimited CI loops ("diminishing marginal returns"). — [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)

#### Cursor — Scaling long-running autonomous coding (2026-01-14, Wilson Lin); Towards self-driving codebases (2026-02-05, Wilson Lin); Expanding our long-running agents research preview (2026-02-12, Cursor Team)
- First design failed: equal agents coordinating through a shared file with locks. "Twenty agents would slow down to the effective throughput of two or three"; "agents could fail while holding locks". Optimistic concurrency was "simpler and more robust" but "With no hierarchy, agents became risk-averse. They avoided difficult tasks and made small, safe changes instead." — [Cursor scaling](https://cursor.com/blog/scaling-agents)
- January design: planners (which "can spawn sub-planners"), workers ("don't coordinate with other workers"), and "At the end of each cycle, a judge agent determined whether to continue, then the next iteration would start fresh." — [Cursor scaling](https://cursor.com/blog/scaling-agents)
- Figures: browser project "ran for close to a week, writing over 1 million lines of code across 1,000 files"; Solid to React migration "took over three weeks with +266K/-193K edits. It still needs careful review"; video rendering "25x faster". — [Cursor scaling](https://cursor.com/blog/scaling-agents)
- Models by role: "GPT-5.2 models are much better at extended autonomous work... Opus 4.5 tends to stop earlier and take shortcuts when convenient... GPT-5.2 is a better planner than GPT-5.1-Codex... We now use the model best suited for each role rather than one universal model." — [Cursor scaling](https://cursor.com/blog/scaling-agents)
- "We initially built an integrator role for quality control and conflict resolution, but found it created more bottlenecks than it solved." "The harness and models matter, but the prompts matter more." — [Cursor scaling](https://cursor.com/blog/scaling-agents)
- February post gives the full sequence of designs: (1) single agent nudged to "keep going" ("lost track of what it was doing, frequently stopped to proclaim success"); (2) manual dependency-graph fan-out; (3) self-coordination via shared file (failed); (4) planner, executor, workers, judge ("bottlenecked by the slowest worker. It was too rigid."); (5) continuous executor with the judge removed, which then "would sleep randomly, stop running agents, do work itself, refuse to plan and spawn more than a few narrowly focused tasks, not properly merge worker changes, and claim premature completion" because "it was being given too many roles and objectives simultaneously"; (6) final: recursive planners and isolated workers. — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Final design: root planner "does no coding itself. It's not aware of whether its tasks are being picked up or by whom." Workers "work on their own copy of the repo, and when done, they write up a single handoff that the system submits to the planner that requested the task." The handoff "contains not just what was done, but important notes, concerns, deviations, findings, thoughts, and feedback." — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Throughput: "The system peaked at ~1,000 commits per hour across 10M tool calls over a period of one week. Once the system started, it didn't require any intervention from us." Infrastructure: "a single large Linux VM"; "most runs would peak at several hundred agents"; the disk became the hotspot. — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Verification stance: "When we required 100% correctness before every single commit, it caused major serialization and slowdowns... Workers would go outside their scope and start fixing irrelevant things." Instead "the ideal efficient system accepts some error rate, but a final 'green' branch is needed where an agent regularly takes snapshots and does a quick fixup pass before release." — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Freshness mechanisms: "A scratchpad.md should be frequently rewritten versus being appended to"; automatic summarization at context limits; self-reflection reminders. — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Prompting lessons: "Constraints are more effective than instructions. 'No TODOs, no partial implementations' works better than 'remember to finish implementations.'"; "'Generate 20-100 tasks' conveys the intent is larger scope"; "Treat the model like a brilliant new hire who knows engineering but not your specific codebase". — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Specification failures: "Our first version of the simple browser without JavaScript converged on an architecture that was unfit to evolve into a full browser. This was a failure of the initial specification."; vague "spec implementation" sent agents "deep into obscure, rarely used features". "Agents have immense engineering skill but will follow instructions to the end, good or bad." — [Cursor self-driving](https://cursor.com/blog/self-driving-codebases)
- Product version: "Long-running agents in Cursor propose a plan and wait for approval instead of immediately jumping into execution" and "use a plan and multiple different agents checking each other's work". Example runtimes 36, 30 and 25 hours; a user quote cites "a 52-hour task... a big PR with 151k lines of code". "long-running agents produced substantially larger PRs with merge rates comparable to other agents" (chart not read). — [Cursor long-running](https://cursor.com/blog/long-running-agents)
- Open issue: "we'll need new approaches to deploying that code to production safely." — [Cursor long-running](https://cursor.com/blog/long-running-agents)
- **Correction to earlier notes**: it was the continuous *executor* (not the planner) that was overloaded with too many roles; the judge was removed before that, and the integrator was removed separately as a bottleneck.

#### StrongDM — Software Factories And The Agentic Moment (2026-02-06, Justin McCarthy) and the Principles, Techniques, DTU and Attractor pages
- "We built a Software Factory: non-interactive development where specs + scenarios drive agents that write code, run harnesses, and converge without human review." Rules: "Code must not be written by humans"; "Code must not be reviewed by humans"; "If you haven't spent at least $1,000 on tokens today per human engineer, your software factory has room for improvement". — [StrongDM](https://factory.strongdm.ai/)
- Team: founded "July 14th, 2025" by Justin McCarthy (co-founder, CTO), Jay Taylor and Navan Chauhan. Catalyst: "with the second revision of Claude 3.5 (October 2024), long-horizon agentic coding workflows began to compound correctness rather than error." — [StrongDM](https://factory.strongdm.ai/)
- What failed: tests alone. "the agent, obsessed with the immediate task, soon began to take shortcuts: return true is a great way to pass narrowly written tests". "A test, stored in the codebase, can be lazily rewritten to match the code. The code could be rewritten to trivially pass the test." — [StrongDM](https://factory.strongdm.ai/)
- Scenarios: "an end-to-end 'user story', often stored outside the codebase (similar to a 'holdout' set in model training), which could be intuitively understood and flexibly validated by an LLM." Satisfaction: "of all the observed trajectories through all the scenarios, what fraction of them likely satisfy the user?" — [StrongDM](https://factory.strongdm.ai/)
- Digital Twin Universe: "behavioral clones of the third-party services our software depends on. We built twins of Okta, Jira, Slack, Google Docs, Google Drive, and Google Sheets"; "thousands of scenarios per hour without hitting rate limits". Method: "We build test doubles from API contracts and observed edge cases, then validate them against the live dependency until we stop finding behavioral differences." — [StrongDM](https://factory.strongdm.ai/); [StrongDM DTU](https://factory.strongdm.ai/techniques/dtu)
- Principles: "Seed → Validation harness → Feedback loop. Tokens are the fuel." "The loop runs until the holdout scenarios pass (and stay passing)". — [StrongDM Principles](https://factory.strongdm.ai/principles)
- Validation constraint: "Code was treated analogously to an ML model snapshot: opaque weights whose correctness is inferred exclusively from externally observable behavior." — [StrongDM Techniques](https://factory.strongdm.ai/techniques)
- Attractor: "It composes models, prompts, and tools into a graph-structured pipeline." "Edges between nodes are expressed in natural language and evaluated by the LLM." Properties listed: "Deterministic given the same inputs", "Observable at every node transition", "Resumable from any checkpoint", "Composable with other graphs". The page lists about 20 community implementations (Rust, Go, Python, Java, F#, C, Ruby, Scala, TypeScript and others); several add human approval gates and route models per node via stylesheets. — [StrongDM Attractor](https://factory.strongdm.ai/products/attractor)
- The DTU page's title tag reads "Digital Twin Users" while the body says "Digital Twin Universe". — [StrongDM DTU](https://factory.strongdm.ai/techniques/dtu)
- **Correction to earlier notes**: orchestrators_and_protocols.md says a factory spending $1,000 per engineer per day "still has room for improvement". The actual rule is the reverse: if you have *not* spent at least $1,000 that day, there is room for improvement.

#### Spotify — Honk, Parts 1 to 4 (2025-11-06, 2025-11-24, 2025-12-09, 2026-04-22; Parts 1 to 3 by Max Charas and Marc Bruggmann)
- Base: Fleet Management runs source transformations as containerized jobs that open PRs; "Since mid-2024, around half of Spotify's pull requests have been automated by this system." The agent replaced only the transformation step: "All the surrounding Fleet Management infrastructure — targeting repositories, opening pull requests, getting reviews, and merging into production — remains exactly the same." — [Spotify Part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)
- Swappable harness: "we decided to build a small internal CLI. Crucially, having that CLI allows us to seamlessly switch between different agents and LLMs... has already allowed us to swap out pieces multiple times". — [Spotify Part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)
- Figures: "more than 1,500 pull requests"; "a total time saving of 60–90% compared to writing the code by hand"; "hundreds of developers now interact with our agent". - Harness history: tried Goose and Aider ("It was difficult to get them to reliably produce mergeable PRs"); then a homegrown loop with "10 turns per session, three session retries total", which "often ran out of turns" and "tended to get lost when it filled up its context window"; then Claude Code: "our top-performing agent, which we've applied for about 50 migrations and the majority of the background agent PRs merged into production." — [Spotify Part 2](https://engineering.atspotify.com/2025/11/context-engineering-background-coding-agents-part-2)
- Prompt lessons: "Tailor prompts to the agent"; "State preconditions... clearly state in the prompt when not to take action"; "Use examples"; "Define the desired end state, ideally in the form of tests"; "Do one change at a time"; "Ask the agent for feedback on the prompt." "Notably, we don't currently have code search or documentation tools exposed to our agent." - Admitted weakness: "we are still flying mostly by intuition. Our prompts evolve by trial and error. - Three failure modes, ranked: no PR ("minor annoyance"); PR fails CI ("frustrating"); "a PR that passes CI but is functionally incorrect. This is the most serious error, as it erodes trust in our automation." — [Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
- Verifiers: "the agent doesn't know what the verification does and how, it just knows that it can (and in certain cases must) call it". Verifiers activate by repo contents (a Maven verifier if pom.xml exists), return trimmed errors, and run before any PR: "In the case of Claude Code, we do this with the stop hook. If one of the verifiers fails, the PR isn't opened". — [Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
- Judge: "It uses the diff of the proposed change and the original prompt, and sends them to an LLM for evaluation." "We have yet to invest in evals for our judge. However... out of thousands of agent sessions, the judge vetoes about a quarter of them. When that happens, the agent is able to course correct half the time... the most common trigger is the agent going outside the instructions outlined in the prompt." — [Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
- Isolation: "The agent runs in a container with limited permissions, few binaries, and virtually no access to surrounding systems." "Pushing code, interacting with users on Slack, and even the authoring of prompts are all managed by surrounding infrastructure." Limits: verifiers "only run on Linux x86"; no CI outer loop yet. — [Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)
- Part 4 case study: two deprecated datasets with "~1,800 direct downstream data pipelines"; an estimated "10 engineering weeks" manually; "we successfully rolled out 240 automated migration PRs using Fleetshift." — [Spotify Part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)
- Part 4 failures: Scio pipelines were abandoned ("We therefore made the decision not to continue trying to make Scio migrations work at that time"); a context file generated by repurposing a human migration guide "was not comprehensive enough, and Honk was left to make assumptions about how to map from one dataset field to another that were often incorrect" until explicit mapping tables were added; and because dbt and BigQuery Runner repos "rarely used any build-time unit testing... we had to rely on the downstream owning teams to perform their own manual testing before merging". Where judgment was needed, Honk was told "to leave the fields unchanged, but to add comments above them with links to human engineer migration guides". — [Spotify Part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)
- **Note on earlier notes**: Part 1 date is 6 November 2025. The judge veto wording is "about a quarter", with course correction "half the time". These posts do not mention removing the judge; that claim rests on a secondary source I did not read.

#### Simon Willison — Embracing the parallel coding agent lifestyle (2025-10-05); The Five Levels (2026-01-28); How StrongDM's AI team build serious software without even looking at the code (2026-02-07)
- On review as the limit: "AI-generated code needs to be reviewed, which means the natural bottleneck on all of this is how fast I can review the results." Parallel work he finds useful: research and proofs of concept, explaining how a system works, small maintenance tasks, and "carefully specified and directed actual work" ("Code that started from your own specification is a lot less effort to review"). — [Willison, Oct 2025](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- His isolation practice then: YOLO mode "for tasks where I'm confident malicious instructions can't sneak into the context"; "I haven't adopted git worktrees yet: if I want to run two agents in isolation against the same repo I do a fresh checkout, often into /tmp"; asynchronous cloud agents "For riskier tasks". — [Willison, Oct 2025](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Five levels (Dan Shapiro): spicy autocomplete; coding intern; junior developer; developer; engineering team; "The dark software factory, like a factory run by robots where the lights are out because robots don't need to see." Of the team he saw: "The goal of the system is to prove that the system works. A huge amount of the coding agent work goes into testing and tooling and simulating related systems and running demos." Later updated to say the team was StrongDM's. — [Willison, Jan 2026](https://simonwillison.net/2026/Jan/28/the-five-levels/)
- On StrongDM: "This feels like the most consequential question in software development right now: how can you prove that software you are producing works if both the implementation and the tests are being written for you by coding agents?" Holdout scenarios "imitate[s] aggressive testing by an external QA team". The twins were built by dumping "the full public API documentation of one of those services into their agent harness" to produce "a self-contained Go binary"; Jay Taylor's tip: "Use the top popular publicly available reference SDK client libraries as compatibility targets, with the goal always being 100% compatibility." — [Willison, Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- Attractor's repo "contains no code at all—just three markdown files describing the spec"; cxdb is "16,000 lines of Rust, 9,500 of Go and 6,700 of TypeScript". - His reservation, under the heading "Wait, $1,000/day per engineer?": "If these patterns really do add $20,000/month per engineer to your budget they're far less interesting to me. At that point this becomes more of a business model exercise". — [Willison, Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)

#### Anthropic — Harness design for long-running application development (2026-03-24, Prithvi Rajasekaran); Managed Agents (2026-04-08; Lance Martin, Gabe Cemaj, Michael Cohen); Effective harnesses for long-running agents (2025-11-26); multi-agent research system (2025-06-13)
- Two failure modes: loss of coherence and "context anxiety" as the window fills, and lenient self-evaluation: "agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre." "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work". — [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Three agents: planner (turns "a simple 1-4 sentence prompt" into a spec, kept high-level so spec errors do not "cascade into the downstream implementation"), generator (sprints, one feature at a time), evaluator (uses "the Playwright MCP to click through the running application the way a user would"; "Each criterion had a hard threshold, and if any one fell below it, the sprint failed"). Before each sprint the two "negotiated a sprint contract: agreeing on what 'done' looked like". "Communication was handled via files". — [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Costs: retro game maker, solo 20 min and $9 versus full harness 6 hr and $200 ("over 20x more expensive"); the solo app's core feature was broken. Sprint 3 alone had 27 contract criteria. — [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Evaluator tuning: "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway." — [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Simplification with Opus 4.6: sprints removed; evaluator moved to a pass at the end. DAW run: planner 4.7 min/$0.46; build rounds 2 hr 7 min/$71.08, 1 hr 2 min/$36.89, 10.9 min/$5.88; QA rounds $3.24, $3.09, $4.06; total 3 hr 50 min, $124.70. "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." — [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Principle: "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing"; a first radical simplification failed, so components were removed "one component at a time". — [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Managed Agents virtualizes three parts: "a session (the append-only log of everything that happened), a harness (the loop that calls Claude and routes Claude's tool calls to the relevant infrastructure), and a sandbox". The first design, everything in one container, failed: "we'd adopted a pet... if a container failed, the session was lost", and debugging meant opening a shell in a container that "often also held user data". — [Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents)
- After decoupling, the harness calls the container as a tool, "execute(name, input) → string"; a crashed harness is restarted with "wake(sessionId)" and reads the log. Security: "make sure the tokens are never reachable from the sandbox where Claude's generated code runs"; Git tokens are wired into the remote at init, and MCP calls go through a proxy that fetches credentials from a vault. — [Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents)
- Result: "our p50 TTFT dropped roughly 60% and p95 dropped over 90%." Dead-weight example: context resets added for Sonnet 4.5 were unnecessary on Opus 4.5 ("The resets had become dead weight"). — [Anthropic Managed Agents](https://www.anthropic.com/engineering/managed-agents)
- Earlier harness (Nov 2025): initializer agent writes a JSON feature list ("over 200 features" for a claude.ai clone, all marked failing), an init.sh and a progress file; coding agents do one feature per session and commit. Failure modes named: trying "to one-shot the app"; a later instance would "declare the job done"; marking features complete "without proper testing" until told to use browser automation. — [Anthropic effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Multi-agent research (Jun 2025): Opus 4 lead with Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; "token usage by itself explains 80% of the variance"; "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats"; lead agents "execute subagents synchronously". — [Anthropic multi-agent](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- Reading in full shows a common arc that excerpts hid: every team reports a first design that failed (Cursor's shared lock file and overloaded executor; Spotify's Goose/Aider trial and homegrown loop; StrongDM's tests that agents gamed; Anthropic's single container and self-grading generator; the DeepSeek single session that would not delegate). The fixes converge on removing capabilities from a role instead of prompting it to behave.
- Three sources independently hold that a coordinator should not execute: Cursor's root planner "does no coding itself", DeepSeek's Router "can run without a Bash tool at all", and Gumloop's worker "hands the job to a coding agent".
- Two sources hide the verifier's internals from the agent: Spotify ("the agent doesn't know what the verification does") and StrongDM (scenarios held outside the codebase). Both are responses to agents gaming or wandering.
- The harness is treated as replaceable by Gumloop, Spotify, Ramp ("supports all frontier models"), Attractor implementations and Anthropic Managed Agents; Stripe is the exception with a long-lived internal fork. Cursor picks models per role.

## 4. For each system: unit of work, isolation, harness/model choice, verification, human approval, and what did not work

### Takeaway
All of them isolate one agent per task and gate on machine-checkable proof; they differ mainly on who merges (a human everywhere except StrongDM and Cursor's research runs) and on whether the harness is a swappable part.

### Inferences
- Verification strength, not agent capability, sets the ceiling on autonomy in every account. Spotify's Part 4 is the clearest negative case: where repos had no tests, the agent's self-check was "unavailable" and review reverted to manual testing by owners.
- Human approval sits in one of three places: before work (Cursor's plan approval), during work on judgment calls (Gumloop's Slack question with a recommended pick), and at merge (Gumloop, Stripe, Ramp, Spotify). Only Gumloop documents remembering the mid-work answers so the same question is not asked twice.
- Reported output metrics are not comparable across sources: PRs per week (Stripe, Gumloop), share of merged PRs (Ramp), cumulative PRs (Spotify), commits per hour (Cursor), tokens per engineer per day (StrongDM). Only Gumloop publishes a breakdown of how merged PRs were touched by humans.
- For a factory extended beyond code, the transferable parts are the ones that do not depend on a test suite: lines with named owners, an issue tracker as the system of record, escalation with a recommended pick, remembered preferences, and a separate evaluator with explicit criteria (Anthropic's design-grading experiment is the only primary evidence here of evaluator loops on subjective output).

### Gaps
- None of these sources reports post-merge defect, revert or incident rates for agent-written changes.
- None describes a non-code line in operation; Gumloop only asserts the shape transfers.
- Cost per merged change is given by no one; only Anthropic (per run) and StrongDM (a spending norm) give money figures.
